---
name: ZBS internal template library
description: Product boundary for EasyEdu's internal ZBS message-template authoring library.
---

Keep the internal ZBS template library separate from the legacy `notification_templates` catalog, OA template mappings, all existing message-sending services, and payment flows. Its drafts may model text, variables, image resources, and action buttons, but image/button compatibility and preview rendering remain unverified until validated for the relevant ZBS template type.

The rollout is intentionally two-phase. Current phase: an administrator creates ZBS templates directly in the customer's Zalo OA, gets Zalo approval, then maps/imports those existing OA templates into EasyEdu and stores the OA-specific IDs and statuses. Use this accumulated approved content to establish and finalize system-standard canonical templates. Future phase: once those standards are confirmed, automatically create them on each customer's OA and track each OA's separate template IDs and review statuses. Do not reverse the current manual-first flow or start provisioning early.

For payment templates, bank code, account name, and bank account are fixed template content, not send-time parameters. The future per-center creation flow should populate those fixed fields from that center's bank settings when creating its own OA template; each new template is submitted to Zalo review and gets an OA-specific ID. Saving the source template definition in EasyEdu does not alter the already-approved source template.

The intended onboarding behavior is to prepare/create a center's OA templates when it connects its OA, pre-filling payment details from that center's settings. If bank details are missing, leave the EasyEdu setup pending for the center to complete; do not submit empty or dummy PAYMENT values. Current Zalo component docs require bank_code, account_name, and bank_account as fixed non-empty text.

Zalo's documented read APIs provide OA template IDs/names/status and a separate sample-data endpoint for parameter examples, but do not expose the full approved layout/components for retrieval. Exact replication therefore requires capturing the source layout from ZBS Account or receiving its original create/edit payload; do not claim a screenshot or sample-data response is the full canonical definition.

The editor's three main cards are: template information (name, code, notification type, title), content (text, variable insertion, media, QR, and preview), and button assignment. Variables belong in the content workflow, not in the first card.

**Why:** The user clarified the intended sequence: first create and approve templates directly in each customer's Zalo OA, then map and save them in EasyEdu; use these mappings/approved definitions to establish system-standard templates, and only later automate creating those standards on customer OAs. Payment account fields are fixed template content and must be populated from each center's bank settings before future automated creation; Zalo review is asynchronous.

**How to apply:** Preserve the manual-first phase: let an administrator create templates on the OA and map/import the approved OA-specific records into EasyEdu, keeping IDs/statuses per OA. Build the system-standard canonical catalog from definitions the user has finalized; distinguish it from drafts and OA-specific mappings. Capture exact layouts from ZBS Account or original create/edit payloads; do not treat template list/sample-data APIs as full layouts. Automatic provisioning is a later phase and must not begin until explicitly requested and canonical definitions are confirmed. At that point, prefill fixed bank details from each center's settings; if required data is missing, leave provisioning pending instead of submitting empty/dummy values, and track Zalo's review status. Preserve existing OA sending, automated messages, payment flows, and ZBS mappings. Do not connect the library to NotificationService/ChannelResolver without a separate explicit request and verified compatibility. Do not drop legacy ZNS-named shared tables or columns as part of retiring the sender.
