---
name: ZBS internal template library
description: Product boundary for EasyEdu's internal ZBS message-template authoring library.
---

Keep the internal ZBS template library separate from the legacy `notification_templates` catalog, OA template mappings, all existing message-sending services, and payment flows. Its drafts may model text, variables, image resources, and action buttons, but image/button compatibility and preview rendering remain unverified until validated for the relevant ZBS template type.

The product roadmap is to maintain exact, canonical definitions of approved ZBS templates in EasyEdu, then later create those templates automatically on each connected center's OA. Keep the canonical approved content and parameter schema separate from per-OA Zalo template IDs/mappings. Do not start automatic OA creation until explicitly requested.

For payment templates, bank code, account name, and bank account are fixed template content, not send-time parameters. The future per-center creation flow should populate those fixed fields from that center's bank settings when creating its own OA template; each new template is submitted to Zalo review and gets an OA-specific ID. Saving the source template definition in EasyEdu does not alter the already-approved source template.

The intended onboarding behavior is to prepare/create a center's OA templates when it connects its OA, pre-filling payment details from that center's settings. If bank details are missing, leave the EasyEdu setup pending for the center to complete; do not submit empty or dummy PAYMENT values. Current Zalo component docs require bank_code, account_name, and bank_account as fixed non-empty text.

Zalo's documented read APIs provide OA template IDs/names/status and a separate sample-data endpoint for parameter examples, but do not expose the full approved layout/components for retrieval. Exact replication therefore requires capturing the source layout from ZBS Account or receiving its original create/edit payload; do not claim a screenshot or sample-data response is the full canonical definition.

The editor's three main cards are: template information (name, code, notification type, title), content (text, variable insertion, media, QR, and preview), and button assignment. Variables belong in the content workflow, not in the first card.

**Why:** The user said ZNS was never used, OA automation is active, and EasyEdu is moving toward ZBS templates; the user also explicitly requires this work to leave current OA, automated-message, and payment flows unchanged. The user later clarified that the future system should seed approved canonical templates onto each center's connected OA, after the exact approved definitions are stored centrally, and should prefill each center's bank information, letting the center complete missing details. Current Zalo documentation identifies payment account fields as required fixed content, requires review for created templates, and does not expose the complete approved layout through the documented read APIs.

**How to apply:** Keep editable drafts center-scoped and in draft/unverified state. Store exact approved ZBS definitions as canonical templates distinct from drafts and OA-specific IDs/mappings. Capture the source layout from ZBS Account or its original create/edit payload; do not use template list/sample-data APIs as a substitute for layout. When later provisioning payment templates, prefill the center's fixed bank fields; if any are missing, leave setup pending until the center completes them rather than submitting blank/dummy values. Expect each created template to require review. Use the three-card editor structure above when changing the authoring form. Preserve existing OA sending, automated messages, payment flows, and ZBS mappings. Do not create templates on OAs, send messages, or connect the library to NotificationService/ChannelResolver without a separate explicit request and verified compatibility. Do not drop legacy ZNS-named shared tables or columns as part of retiring the sender.
